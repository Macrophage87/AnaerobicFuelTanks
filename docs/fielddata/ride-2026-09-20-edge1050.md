# Field ride 2026-09-20, Edge 1050, v0.8: evidence note

The first ride this app recorded that is committed as regenerable evidence
(`docs/agents/rituals/FIELD_DATA.md` §1). Every figure below is printed by
`tools/fielddata/ride_evidence.py` from the committed fixtures
`tools/fielddata/fixtures/ride-2026-09-20-edge1050.{series.csv,events.csv,inventory.txt}`.
The required `test-tooling` job runs `ride_evidence.py --check` on **this file**
and goes red if the `RIDEFACT` block at the end disagrees with the fixtures in
any way (a changed, missing, extra or reordered line). The prose is not checked.
Each claim in it names the `RIDEFACT` key it rests on.

## Provenance

* **Source:** `i188577527.fit`, recorded 2026-09-20 by the maintainer on an Edge 1050
  (`garmin_product` 4440, firmware 32.2). Per #117 the build was v0.8. The fixture
  header does not record the app version. The `.fit` is **not committed**
  because it carries GPS and heart rate.
* **Extraction:** `tools/fielddata/extract_ride_fixture.py` (fitparse, `check_crc=True`),
  run outside CI because CI has no `.fit`. Anyone holding the original re-runs it and
  must get byte-identical fixtures. The fixture headers carry the provenance, the
  absence encoding (an empty cell is an absent field, never 0) and the latch
  caveat.
* **What was dropped on purpose:** GPS, heart rate, absolute timestamps, and every
  other app's *values*. The inventory keeps only what the other apps *declared*.

## What this ride establishes

1. **This app declared exactly its two fields.** Under `developer_data_index` 3 there
   are two `field_description`s: `PCr_J` (field 0) and `GLY_J` (field 1), both
   `float32`, units `J`, on `record` (`ours_fields`). The app contributes nothing to
   `session` (`devbytes session 3 0`) and 8 B to `record` (`devbytes record 3 8`).
2. **Populated, bounded and still moving at the end.** Both fields are present on
   11903/11903 records (`populated`). Neither goes negative (`negatives`), and each
   maximum equals its first-record value (`range`). Both are still changing at the last
   record (`last_change`). That last figure matters because a latched field counts as
   populated whether or not anything writes it (`docs/agents/FACTS.md` §3.3). A value
   that moves at the last record shows the model was still stepping.
3. **Capacity inference.** First-record `PCr_J + GLY_J` = 21472 J and fP = 0.2500
   (`capacity_first_sum`, `fP_first`). This equals W′ **only if both tanks were full at
   the first record**. The rider's settings are not in the file, because #102 keeps
   config out of the FIT. #100 reports the same 5368 + 16104 J split for the 2026-07-26
   ride.
4. **The resume latch.** The ride has 23 pause boundaries (`boundaries`). At **all 23**:
   * the first record after the resume repeats the last pre-pause record exactly, for
     both reserves (`boundary_latch`);
   * that record carries no power (`boundary_power_absent_at_resume`);
   * the reserves move at the next record (`boundary_change_at_next`).

   At that next record the move is up at 21/23 (PCr) and 22/23 (GLY)
   (`boundary_next_rise`). Boundaries 2 and 22 are the exceptions: PCr falls there
   (per-boundary `boundary` lines). No record falls inside a pause
   (`records_inside_pauses`). So the rest-recovery refill arrives one record *after*
   the resume, together with whatever that step drew, and not at the first
   post-resume record. That corrects #102 §3.1, which read the opposite off the
   source.
5. **The one-record lag (#100), reproduced on a second ride.** The draw is
   reconstructed from the reserves on 11881 one-second steps (`draw_steps`). Two
   definitions agree, which `FIELD_DATA.md` §5 asks for before a figure counts as a
   finding:
   * Pearson r peaks at lag +1: 0.561, against 0.502 at lag 0 (`lag_r`).
   * The single-threshold fit misclassifies 13/11858 at lag +1, against 488/11879 at
     lag 0 (`threshold`). Its best CP at lag +1 is 255 W, the same figure #100 fit on
     the 2026-07-26 ride.

   #100's correlations (0.599 / 0.738 / 0.822 / 0.680) were computed on the retired
   `PCr_cons`/`GLY_cons` stream. These are computed on a reconstruction from the
   reserves, which is a different definition. The r values are therefore not
   comparable across the two rides; the position of the peak is.
6. **Four co-installed apps declared 49 B on `record`.** Four developer data indexes
   declare fields (`apps`). Declared `record` bytes per index are 13 / 4 / 24 / 8 = 49 B,
   and the largest single app declares 24 B (`devbytes record`). Every byte figure here
   counts one element of each declared base type (the inventory header says so): the
   fixtures carry neither the `field_description` `array` count nor the definition
   messages' developer-field sizes, so an array field would be under-counted. `session`
   totals 21 B and `lap` 12 B. The file holds 49 B of `record` declarations while every
   app's declared elements stay ≤ 32 B, and it saved. That is consistent with #96's per-app budget reading. It is
   one more file.
7. **The application id in the file is not the manifest id** (`app_id`). The file
   carries `24ec02815a2643ac8e47d1f1bc7bceb4`; `connectiq/manifest.xml` carries
   `fc13e61e7ca54c998c7a7c64f0ef4434`. This note does not establish why. The extractor
   matches this app by field **name** for this reason.

## What it does NOT establish

* **Anything with `fitRecord` OFF** (#108 run B, criteria 9–10). This ride is ON only.
* **#108 criteria 11–13.** None of these is in a FIT file: the absence of the load
  banner and log line, whether the settings prompt is visible, and the update over an
  older install.
* **The rider's CP / W′ / fP.** #108 criterion 7's bounds need them. Item 3 above
  assumes full tanks at the first record.
* **That exactly one `developer_data_id` message belongs to this app** (#108
  criterion 1). The fixtures record `field_description`s, not `developer_data_id`
  messages. The extractor does refuse a file whose `PCr_J`/`GLY_J` sit under more than
  one index.
* **The byte `0x88`.** The inventory records fitparse's type name `float32`, not the
  raw `fit_base_type_id`.
* **Any heap figure, and the co-installed OFF/ON A/B** (#112 parts 1 and 2). Four apps
  declaring 49 B in a file that saved is not the A/B: there is no OFF ride, and the
  file says nothing about memory.
* **The other three apps' values.** The fixtures record only what those apps declared.
  Whether they populated their fields is not in the fixtures, by design.
* **Where the offset arises inside the platform.** The ride shows the offset (item 5)
  and the latched resume records (item 4). Both are consistent with the record
  carrying the value from the previous `compute()`. #100's source reading ruled out
  app write-ordering. Nothing here observes the head unit's internal ordering.
* One ride, one device, one firmware.

## A figure that differs from the out-of-tree decode

A direct decode of the `.fit`, made outside the tree before this tool existed, reported
Pearson r = **0.493** at lag +2. This tool prints **0.495** as the primary figure
(`lag_r +2`, 11836 pairs). The 0.493 comes from index-keyed pairing
(`lag_r_index +2`, 11857 pairs). The 21 extra index-keyed pairs sit at the first
one-second step after each of the 21 pauses longer than 1 s (`spacing`). Each pairs
that step's draw with the power of the **pre-pause** record, which was recorded
seconds to minutes earlier. The time-keyed figure is primary because none of its pairs
crosses a pause. Every other figure matches that direct decode.
